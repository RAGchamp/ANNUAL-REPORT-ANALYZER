Steps Needed for Onboarding a New Annual Report

Does every new annual report need new extraction rules? No. Only a report whose layout differs from every model document does. This guide explains how to tell which case you are in and what onboarding involves. It then walks through how the JPMorgan Chase 2025 Form 10-K was onboarded, and why it needed its own model even though a 10-K model (Chubb, TYPE-3) already existed.

1. Short Answer: Is This Needed for Every Report?

No. A model document stands for a layout (how the report is typeset), not for a company or a year. A new report is read automatically when its layout is close enough to one of the models for that model's rules to pass their checks on it. In that case you drop the PDF into Annual-reports\, select it, and analyze. There is nothing to onboard.

Onboarding is needed only when the app shows the yellow "New model document — can't be analyzed until its model is added" box. That means no existing rules could read the report's notes and statements correctly.

What to expect in practice
New reportLikely outcome
Next year's report of a company that is already a model (e.g. JPMorgan 2026, Bharat Forge 2027)Usually matches its own model; companies rarely change their typesetting. Not guaranteed: a redesign can break a rule.
Another company that uses the same typesetting (e.g. another Indian Ind AS integrated report; another 10-K produced by an EDGAR filing agent like Chubb's)Often matches an existing model.
A company that designs its own report (its own fonts, columns and note headings), even with the same form typeOften needs onboarding. JPMorgan is this case: it is a Form 10-K like Chubb's, but it is typeset quite differently.
A different country, accounting framework or eraUsually needs onboarding (new wording checks, at least).

The more formats are onboarded, the more often a new report matches, or needs only a small profile made from switches that already exist (Section 9).

2. How the App Decides: Matching

When you select or re-ingest a report, the ingester matches it to a model document before it extracts anything (WEB-APP\ingest\models\match.py):

1. Checksum      the PDF is a model document itself?           ─► matched
2. Fingerprint   fonts, page shape, form (10-K, 20-F…), framework (US GAAP, Ind AS…),
                 currencies, note-heading styles, statement titles…  ─► similarity to every model
3. Trial         the best 3 models (with rules) above 0.55 similarity:
                 extract the report with each model's rules
4. Acceptance    did that extraction find ≥ 5 notes numbered from about 1, ≥ 3 of the 4 statements,
                 readable figures, a balance sheet that balances, and the format's wording?
                 ─► the first model whose checks all pass is the match
                 ─► none passes (or two formats are equally close): NEW MODEL DOCUMENT + gap report

The decision is made by the trial extraction, not by the similarity score. A report can look 71 % like Chubb and still be refused, because Chubb's rules find nothing in it. That is exactly what happened with JPMorgan.

Words used in this guide
TermMeaning
Model documentOne PDF in MODEL-DOCS\ that stands for one report layout. Its id is its file name, TYPE-<n>-<COUNTRY>-<FORM>-<YEAR>-<Company>.
ProfileThe extraction rules for a layout (WEB-APP\ingest\profiles\__init__.py): the indexer, the switches it turns on, and its acceptance checks.
SwitchAn optional rule that only the profiles needing it turn on. A new layout never changes another layout's code path, so existing reports keep exactly the same extraction.
Gap reportWhat the matcher writes for a refused report: its fingerprint next to the nearest models', and what each model's rules found. Opened with View gap report on the Ingest screen.
Quality reportWhat one ingestion found: notes, statements, figures, links, checks, narrative pages. Printed by python -m ingest <pdf>.

3. Which Case Am I In?

CHECK — Drop the PDF in Annual-reports\ and select it
Annual-reports\<report>.pdf→Analyze screen, step 1 (or the Ingest screen)
  • It loads and shows notes and statements: it matched a model. Glance at the quality summary (notes found, statements, "balance checks ok") and analyze. Done.
  • "New model document": onboarding is needed. Read the box: it names the nearest model and what its rules found (e.g. "0 notes found (need 5); 0 of 4 statements found"). Then follow Section 4.

The same check from the command line, which also prints the gap report's path:

PowerShell — C:\Daya\RAGchamp\ANN-RPT-ANALYZER\WEB-APP
python -m ingest.models match "..\Annual-reports\JP-MORGAN-2025.pdf"
"Try again" does not help

Re-ingesting a refused report gives the same verdict every time: the verdict is remembered and the rules have not changed. The verdict changes only when new rules are added (which bumps the registry version and re-matches the report automatically).

4. The Onboarding Steps (General)

These are the steps of the routine in MODEL-DOCS\README.md. You do steps 1 and 7; a Claude Code session in the project does 2–6. The exact prompt to give it is in INFO\HOW-TO-TRAIN-NEW-MODEL-FORMAT.html, Step 3.

STEP 1 — Model document
MODEL-DOCS\TYPE-<next>-<COUNTRY>-<FORM>-<YEAR>-<Company>.pdf

Copy the report into MODEL-DOCS\ under the next TYPE number. Keep a copy in Annual-reports\ to analyze.

STEP 2 — Diagnose

Read the gap report, then look at the PDF's real pages: where the notes start and end, how note headings are printed, where the statements are, what the running headers and footers look like. Run the nearest model's rules and see where each one fails. This is most of the work.

STEP 3 — Profile and switches
WEB-APP\ingest\profiles\__init__.py

Make a new profile, usually with derive() from the nearest one. Where the layout needs new logic, add a switch, write the rule so it only runs when the switch is on, and turn it on in the new profile only. Never change another layout's code path.

STEP 4 — Register and iterate on the quality report

python -m ingest.models register … --profile <id>, then python -m ingest <pdf> --force and read the quality report. Fix, re-ingest, repeat until notes, statements, figures, checks and narrative pages are all right.

STEP 5 — Golden test
WEB-APP\tests\test_<name>.py

Pin down what a correct extraction looks like: note count and a known note's pages, statement pages, a figure with its period, a link, and one test for each new rule.

STEP 6 — Verify nothing else changed

python -m ingest.models verify (every model still matches itself; no other format's rules accept another model) and python -m pytest -q (all tests, including the frozen prompts of the five sample reports, which prove they are byte-identical).

STEP 7 — Try it in the app, then rebuild the exe

Restart python app.py, select the report, check pages on the Model testing screen, ask one question, and rebuild the exe with the dashboard builder.

5. Why JPMorgan Did Not Match Chubb

What the app said
Ingest screen — JP-MORGAN-2025.pdf
New model document — can't be analyzed until its model is added
Nearest: TYPE-3 USA 10-K 2025 Chubb (similarity 0.71); with its rules: 0 notes found (need 5);
0 of 4 statements found (need 3); doesn't mention Item 8.

Both reports are US Form 10-Ks under US GAAP, so they look similar on paper (similarity 0.71). But Chubb's 10-K is typeset by an EDGAR filing agent, and JPMorgan prints its 10-K like a designed annual report. The rules read layout, and the layouts differ:

Text columnsOne columnTwo columns of 10pt text, tables inside a column or across the pageLeft and right lines merged into one sentence

The critical decision: a new model, not a change to Chubb's rules

An alternative was to widen Chubb's profile (us-10k-edgar) until it also read JPMorgan, so the report would match TYPE-3 as expected. That was rejected:

  • Several of the rules are wrong for Chubb's layout. Filling in pages that lack the running header, or reading two columns, would change Chubb's extraction and its frozen prompts.
  • The project rule is one document = one model, and a rule for one layout goes behind a switch, never into another layout's code path.
  • A separate model keeps both formats checked against each other: verify proves Chubb's rules don't accept JPMorgan, and the JPMorgan rules don't accept Chubb.

6. JPMorgan, Step by Step

The order below is the order the work was done in, including the problems found along the way.

STEP 1 — Read the gap report
MODEL-DOCS\_candidates\JP-MORGAN-2025\GAP-REPORT.md

Nearest model TYPE-3 Chubb at 0.71, with 0 notes, 0 statements and no "Item 8" under its rules. The fingerprint showed sans-serif body text at 10pt (Chubb: 7pt, partly serif), 0 % pages with a notes header near the top, and note headings mostly of the "Note N" style. Useful clue for later: 202 PDF bookmarks, 72 usable as report sections.

STEP 2 — Look at the real pages

A short script printed the top rows of the statement and notes pages (font, size, bold, position). Findings:

  • Statements at PDF 167–171, each titled in 12pt bold sentence case ("Consolidated statements of income") under "JPMorgan Chase & Co.".
  • Notes from PDF 172, each starting at the top of a page with Note N – Title in 12pt bold. The only exception: Notes 16 and 17 share p.279, one per column.
  • The header "Notes to consolidated financial statements" is the first row on pages 172, 174, 176… and absent on 173, 175, 177…

Then each statement page was tested on its own with the existing detector, and all four were recognized correctly. So the "0 statements" was not about the statements at all. It came from the notes section starting at the wrong page (p.45, the contents page), which put the statements outside the window searched before the notes.

STEP 3 — New profile us-10k-two-column
WEB-APP\ingest\profiles\__init__.py

Derived from Chubb's us-10k-edgar (same indexer, same "us-10k" format, so the analyzer treats it as a 10-K) with its own switches and a case-insensitive "Form 10-K" / "Item 8" wording check. Narrative sections come from the PDF bookmarks.

STEP 4 — Five switches to find the notes and statements
SwitchProblemRule (only when on)Where
header_starts_rowContents page p.45 taken as a notes pageThe header row must start with the header wordspdf_utils.find_header_row
alternate_header_pagesRight-hand notes pages have no headerA single page between two pages of one notes section belongs to itnotes_index._fill_alternate_pages

First trial build: 34 notes (PDF 172–316) and all 4 statements, with printed page numbers. Three titles were still wrong. "Note 8 – Pension and other postretirement" wraps onto a second line, and "Note 26 – Restricted cash, other restricted" was merged with a bold subheading in the right column. The fix: page rows now also carry their individual spans (parts), so a heading's continuation is taken only from the same column, font and size.

STEP 5 — Read two columns in the right order
WEB-APP\ingest\clip.py→_column_order (switch two_column_text)

Extracted notes came out with the left and right columns interleaved line by line, so the text Claude would read was unusable:

Before — Note 16, p.279
Premises and equipment includes land carried at cost, As of December 31, 2025 and 2024, noninterest-
as well as buildings, leasehold improvements, internal- bearing and interest-bearing deposits were as follows:

The rule finds the gutter (the x in the middle of the page that the fewest characters cross) and reads each band of rows that stays clear of it left column first, then right. Rows that cross the gutter stay whole. So do rows with only figures right of the gutter and table-size labels left of it (a table across the page). A first version decided by font size alone. It merged two small tables set side by side, one per column (Note 25 p.291), so it was refined to look at what is right of the gutter.

STEP 6 — Register TYPE-9 and run the full ingestion

Registry version 12 → 13. The first quality report found two remaining problems: 2 of 4 balance checks ok and 24 statement figures could not be read ("and $286,771 at fair", "value)").

STEP 7 — Fix the bank balance sheet
  • wrapped_label_amounts (tables.py): spans that touch with no space ("Loans (included" + "$70,684" + "and $41,350 at fair value)") are one caption. A first cell that closes an open "(" is caption text, not a figure. A caption with an open "(" continues into the figure row below. Result: Loans (included $70,684 and $41,350 at fair value) | 1,493,429 | 1,347,988.
  • A side effect, caught on the next run: the footnote marker now stuck to "Total assets (a)", so the main total no longer matched and the check fell back to the VIE table (0 of 2 ok). Footnote markers are kept apart, and the balance check ignores a trailing "(a)".
  • first_total_assets_only (links.py): only each balance sheet's first "Total assets" is checked, so the VIE table's 43,295 is not compared with total liabilities and equity.

Result: all statement figures readable, balance checks ok, 0 failed checks.

STEP 8 — A matcher bug found on the way

The ingestion was right, yet the matcher still said "0 of 2 balance checks ok". Its acceptance check ran the balance check outside the profile, so the new switch was off there. ingest\models\acceptance.py now runs it inside the profile. Because acceptance changed, MATCHER_VERSION went 2 → 3, which re-judges remembered "new model" verdicts.

python -m ingest.models match "..\Annual-reports\JP-MORGAN-2025.pdf"
Matched TYPE-9 USA 10-K 2025 JPMorgan (model document, similarity 1.00); profile us-10k-two-column; checks passed
STEP 9 — Golden test, verify, full test suite, docs
  • tests\test_jpm_10k.py: the match and company name; 34 notes with Note 25 = PDF 290–293 (printed 288–291); wrapped titles; Notes 16 and 17 on p.279; statement pages and printed numbers; balance-sheet captions and balance checks; the tax line linked to Note 25; columns read in order; the last body lines kept; Chubb's rules still find no notes in it; the Model testing page.
  • tests\test_models.py: the registry test now expects TYPE-9.
  • python -m ingest.models verify: OK. All nine models match themselves, none is accepted by another format's rules, and every narrative page passes its coverage check.
  • python -m pytest -q: the first full run caught a leak. A variable reused in the note-title code lengthened one of Bharat Forge's sub-headings (Note 54.1), so its frozen prompt changed. It was fixed, and INDEX_VERSION went 34 → 35 so packages built with the bug are rebuilt. The final run: 467 passed, 3 failed. The 3 failures (Chubb's frozen prompts: note-table headings) fail identically on the code as committed before this work, so they are not caused by it (Section 8).
  • Updated: MODEL-DOCS\README.md (TYPE-9 row) and .claude\CLAUDE.md (§2, §7 item 25).

8. Known Limitations

  • Notes 16 and 17 share p.279, one per column. Each note is the whole page, so asking about Deposits also sends the Premises and equipment text (and the reverse). Nothing is lost.
  • Two small tables side by side whose rows on the right are figures only (no labels) can still be read as one row across the page. Check such pages on the Model testing screen if an answer looks odd.
  • "Income tax expense" links to Note 25 by title, not by figure. 15,547 is printed in more notes than the figure-match rule allows. The link is right; its confidence is "medium".
  • The units line ("in millions") is not shown for this report in the package summary; the statements themselves carry "(in millions)".
  • Not in the prompt baseline, like TYPE-6/7/8. Its extraction is pinned by tests\test_jpm_10k.py. Its prompts are not frozen.
  • Chubb's frozen prompts are out of date (not caused by this work). Three Chubb baseline files expect note-table headings without leading empty cells ("Year Ended December 31"). The current code writes " | | | Year Ended December 31", most likely since the aligned_note_columns fix. A checkout of the last commit fails the same way. The baseline should be re-frozen for Chubb once that output is confirmed as wanted.
  • No real Claude analysis was run as part of onboarding. Ask one question (e.g. on Note 25 income taxes) to confirm end to end.

9. What Gets Easier Next Time

Each onboarded layout leaves its switches behind. JPMorgan added eight that any future profile can reuse:

note_word_headings · alternate_header_pages · header_starts_row · two_column_text · footer_page_numbers · us_auditor_addressee · first_total_assets_only · wrapped_label_amounts

So a later report typeset like JPMorgan's, say another large US bank, may match TYPE-9 directly. Or it may need only a derive() that turns on a different mix of existing switches: a few lines, no new code. A report with a layout never seen before still needs the full routine.

Effort to expect

JPMorgan took one Claude Code session: about 8 new switches, about 250 lines of code and tests, two full ingestion iterations after the first build, and a verify plus full test run. Most of the time went into diagnosis (Steps 1–2) and into reading two columns correctly (Step 5). A report that only differs in wording would take minutes.
